## s2_why: Why it breaks (target 0:15-0:35; est.  18.6s to  41.1s, 55 words)

1. Two things break. Context is lost at every hand-off,
2. and agents say done when they aren't.
3. The grader has four cumulative checks: the agent's input crashes the program, its patch stops that crash, the tests still pass, and finally, the benchmark's own hidden crash is gone. Only that last check, S4, is a real fix.

## s3_system: The system (target 0:35-1:05; est.  41.1s to  76.4s, 87 words)

1. Prompt2Own runs each task as a fixed chain: root cause, proof of concept, patch. Every attempt is a fresh Claude Code harness session, driving a GLM model.
2. Guards gate each step. The PoC guard needs a sanitizer crash where the root cause pointed. The patch guard rebuilds, replays the PoC, and runs the tests.
3. Rejections come back with a reason. Accepted facts go into a ledger.
4. Guards never see ground truth, and the grader runs only afterwards. So we can measure false success, and each guard's accuracy.

## s5_findings: What we found (target 1:50-2:35; est. 109.0s to 157.8s, 121 words)

1. On thirty pre-registered tasks, Claude Code as shipped passes the tests on 0.70 but truly fixes 0.43. 40 percent of its success claims are false.
2. Our full system doesn't beat it yet: 0.33, p equals 0.55. Claude Code given our workflow as a prompt reached 0.53. None of these gaps is significant.
3. Verification works unevenly. The PoC guard never accepted a bad PoC: precision 1.00. The patch guard: 0.59. Seven of its seventeen accepts failed S4.
4. In all seven, the agent fixed a real but different bug: the patch fixes my PoC, not the target. False success moves to the weakest check.
5. Splitting also costs: from S1 to S2, P3 falls from 0.70 to 0.57; Claude Code from 0.77 to 0.70.
